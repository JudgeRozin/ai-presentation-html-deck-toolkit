# Element picker — UX contract and implementation notes

A picker baked into the deck HTML: the user points at an element, the deck copies a structured
reference, and that reference is pasted back into the chat. It converts "the blue one, bottom right"
into an instruction a machine can locate exactly.

The implementation lives in `deck.html` in the blocks marked `FEATURE 1 + 2`. This document is the
contract it implements and the reasoning behind the parts that are easy to get subtly wrong.

## UX contract

**Single pick (<kbd>P</kbd> or 🎯)**

- Toggle with `P`; the hotkey is ignored while the user is typing in an `input`, `textarea` or
  `contentEditable`, and `Cmd/Ctrl/Alt+P` is left to the browser.
- In pick mode: crosshair cursor, a fixed banner, cyan outline on the hovered element, and a tooltip
  that follows the cursor showing slide number, DOM path and text.
- On click: reference copied to the clipboard, gold flash on the picked element, toast showing exactly
  what was copied, then pick mode exits on its own.
- <kbd>Esc</kbd> exits without copying.

**Multi pick (<kbd>M</kbd> or 🔲)**

- Panel with a live count and three actions: `Copy refs`, `Clear`, `Exit`.
- Clicking elements accumulates them (each keeps a gold ring); clicking again removes one.
- The <kbd>⊕</kbd> badge in each slide corner selects or deselects the **entire section**.
- The badge is created in JS for every `.slide`, so adding or deleting slides needs no markup change.
- Copy emits one batch: a `# TAG multi-selection (N refs)` header followed by the references in
  **DOM order** (`compareDocumentPosition`), not click order.

**Both modes**

- The picker's own UI, plus every piece of deck chrome, is excluded from picking through a single
  `UI_SEL` selector list checked with `e.target.closest(UI_SEL)`. Without this, clicking the picker's
  own buttons picks them and the user ends up in a confusing loop.
- The click handler is registered in the **capture phase** (`addEventListener('click', fn, true)`) with
  `preventDefault()` + `stopPropagation()`, so deck navigation and any other click handler never fire
  on a pick.
- Clipboard writes fall back to a hidden `textarea` + `execCommand('copy')`: headless contexts and
  some `file://` contexts refuse `navigator.clipboard`.

## Reference format

```
[DECK-TAG] slide 3 · div.pad > article.card · text: "Element Picker" · size 276x216 · css: #slide-3 > div.pad:nth-of-type(1) > article.card:nth-of-type(2)
```

- `DECK-TAG` is per deck, so a reference stays traceable when several decks are in play.
- The readable path is capped at ~4 levels and stops at the slide canvas, keeping the first two class
  names per node: enough for a human to confirm the target, short enough to read.
- The text snippet is capped at 90 characters.
- The CSS path is capped at ~6 levels and stops at the first id. It is disambiguated with
  `:nth-of-type()` because generated markup reuses classes heavily — a class alone rarely identifies
  one element.

## Implementation notes worth keeping

1. **Filter transient highlight classes out of the copied path.** When the reference is built, the
   element carries `.pick-hover` / `.pick-selected` / `.pick-sel`. If those are not filtered in both
   path builders, every reference contains meaningless classes that do not exist on the next load.
2. **`nth-of-type` counting must count siblings of the same tag**, not all previous siblings —
   `while ((sib = sib.previousElementSibling)) if (sib.nodeName === cur.nodeName) nth++`.
3. **Clipboard fallback is mandatory**, not a nicety (see above).
4. **The hotkey guard must skip typing contexts** and modifier combinations, or the picker hijacks the
   user's text and the browser's own print shortcut.
5. **The picker script block goes last**, so deck functions already exist when a pick suppresses a
   click; and it must not re-declare a global the deck already owns (see the `slides` / `toast` note in
   the README).
6. **The tooltip must stay inside the viewport** —
   `left = Math.min(e.clientX + 14, innerWidth - 380)`.

## Agent-side contract

When a `[DECK-TAG] …` reference arrives:

1. Resolve the `css:` path in the deck HTML and confirm the element still exists and matches the text
   snippet. Do not trust the path blindly — the deck may have changed since the reference was copied.
2. Apply the change to the deck source. If the deck is generated by a script, change the generator and
   regenerate, otherwise the next run wipes the edit.
3. Re-verify the affected slide (measure it, or render it) before reporting back.

A `# … multi-selection (N refs)` batch is a single revision pass: apply all N, then confirm the count
so nothing is silently dropped.
